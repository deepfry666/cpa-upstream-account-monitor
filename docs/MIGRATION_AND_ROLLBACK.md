# 0.4.1 到 0.5.0 迁移与回滚

本文适用于从 `0.4.1` 升级到 `0.5.0`，或从失败升级中恢复。迁移会改变偏好文件中的账户 ID、PAT 密文 AAD 和存储格式版本，因此二进制、偏好文件、偏好密钥和快照缓存必须作为一个整体管理。

## 数据文件

默认路径来自 CPA 配置，常见位置为：

```text
/CLIProxyAPI/data/upstream-monitor-preferences.json
/CLIProxyAPI/data/upstream-monitor-preferences.json.key
/CLIProxyAPI/data/upstream-monitor-snapshots.json
plugins/linux/amd64/upstream-monitor.so
plugins/linux/arm64/upstream-monitor.so
```

实际部署可能不同。升级前必须从运行配置中确认 `preferences_path`、`cache_path` 和插件目录，不要只假设默认路径。

## 升级前备份

在不输出 PAT、密钥内容或账户响应的前提下完成：

1. 停止 CPA，确保没有正在写入偏好或缓存。
2. 一起备份旧动态库、偏好文件、偏好密钥和快照缓存。
3. 保留所有文件原权限，密钥文件尤其不能扩大可读范围。
4. 为每个备份计算并记录 SHA-256，记录旧插件版本和 CPA 配置中的存储路径。
5. 在脱敏副本上演练首次加载、第二次启动和回滚，不直接修改唯一备份。
6. 备份不得进入 Git、Release、聊天记录、对象存储公开桶或截图。

没有匹配密钥的偏好备份不能用于恢复 PAT，即使 JSON 文件本身完整。

## 自动迁移行为

### 偏好格式

旧格式读取后升级为 `format_version=2`。迁移包括：

- 已知账户、监控开关、备注、协议覆盖、显示顺序、首次发现时间和查询修订。
- 旧位置型 ID 到稳定 ID 的唯一匹配。
- PAT 旧 ID AAD 解密和稳定 ID AAD 重加密。
- 账号级现金阈值和全局阈值。

旧位置型记录只有在来源类别、规范化地址、来源标识或带密钥指纹能够唯一对应时自动迁移。出现以下情况时标记 `relink_required`：

- 多个旧条目匹配同一个新身份。
- 一个旧条目匹配多个候选。
- 缺少稳定来源标识和可验证指纹。
- Key 已轮换，无法证明新旧身份相同。

`relink_required` 不会继承旧 PAT。用户需要在管理页面确认账户并重新输入 PAT；旧记录仍保留，不会按列表位置猜测。

### PAT 密文

PAT 使用 AES-GCM，账户 ID 作为附加认证数据。迁移过程是：

1. 使用旧账户 ID 解密旧密文。
2. 使用新稳定账户 ID 重新加密。
3. 原偏好密钥保持不变。
4. 原子替换偏好文件。

迁移失败时不覆盖旧密文。状态可能为 `missing`、`ready`、`decrypt_error` 或 `relink_required`。`decrypt_error` 表示密文存在但当前密钥无法解密；只恢复另一把错误密钥不会解决问题。

### 快照缓存

缓存读取顺序：

1. 顶层 `format_version` 包装的当前格式。
2. 无版本 `entries` / `history` 格式。
3. 0.4.x 账户 map 格式。

读取成功后校验账户 ID、必需时间、历史上限和结构，再一次性替换内存。未知未来版本、截断 JSON 和字段冲突会保留原文件并报告失败。0.5.0 写入新缓存时使用格式版本 2、同目录临时文件、文件同步、原子重命名和目录同步。

## 升级流程

1. 完成备份和校验。
2. 从 Release 下载架构匹配的 0.5.0 包，并验证 ZIP 的 SHA-256。
3. 解压后保持文件名为 `upstream-monitor.so`。
4. 替换旧动态库，保留 `preferences_path`、密钥路径和 `cache_path` 配置不变。
5. 启动 CPA，观察插件注册和配置加载是否成功。
6. 打开“数据状态”，确认偏好 revision、目录同步时间和缓存恢复状态。
7. 打开“供应商配置”，检查每账户 PAT 状态。需要时重新关联或重新认证。
8. 执行重新加载、刷新当前、刷新全部各一次，确认任务计数和字段组状态。
9. 停止并再次启动 CPA，确认第二次启动不重复迁移、不重复追加历史，账户顺序和历史保持一致。
10. 在 AMD64 / ARM64 各自环境完成加载检查后再扩大部署。

第一次升级发生时，旧的成套备份必须保留到多平台加载和第二次启动验证完成。

## 升级失败处理

按错误类型处理：

- 偏好未来版本：停止写入，保留文件；不要删除 `format_version` 后重试。
- 偏好损坏：恢复升级前偏好和密钥整套备份，不要只修复 JSON 中可见的一部分。
- `decrypt_error`：恢复原来的匹配密钥；若密钥不可恢复，保留密文，重新输入需要 PAT 的账户。
- 缓存未知版本或截断：保留原文件，插件可继续以空缓存启动；需要历史时恢复升级前缓存。
- 快照写盘失败：配置可能已经成功保存。检查目录权限和剩余空间，不要把配置失败与缓存失败混为一谈。
- 目录同步失败：保留上次成功目录，修复 `source_config_path` 或宿主读取权限后重试同步。

任何诊断输出都必须先脱敏。不要为了排错打开包含真实 PAT 的日志、截图或浏览器网络导出。

## 回滚到 0.4.1

0.4.1 不能直接读取 0.5.0 的偏好格式、稳定账户 ID 和缓存格式。回滚不是只替换 `.so`。

完整回滚步骤：

1. 停止 CPA。
2. 再次备份当前 0.5.0 偏好、密钥、缓存和动态库，便于以后重新升级。
3. 恢复升级前同一时间点的 0.4.1 动态库。
4. 恢复对应的旧偏好文件、旧偏好密钥和旧快照缓存。
5. 保持文件权限与备份时一致。
6. 启动 CPA，确认旧版本能够读取偏好和缓存。
7. 检查账户列表、PAT 状态、历史和基础查询，确认回滚后没有混用。

只恢复旧 `.so` 而不恢复旧数据，可能造成偏好不识别、PAT 解密失败或历史缺失。只恢复旧偏好而不恢复旧密钥，会使已有 PAT 不可解密。

## 回滚的数据影响

回滚会回到升级前备份时点：

- 升级后新增或重新关联的账户监控记录不会出现在 0.4.1。
- 升级后产生的快照和历史不会出现在旧缓存。
- 升级后修改的备注、阈值、协议覆盖和 PAT 不会出现在旧偏好。
- CPA 自身的 Provider、认证文件、路由和配置不会因本插件回滚而改变。

如果维护窗口允许，应在回滚前导出不含凭证的 0.5.0 报告或截图，作为事后对照；报告仍可能包含账户名称和余额，应按内部数据政策保管。

## 验证清单

- [ ] 升级前备份包含二进制、偏好、密钥和缓存。
- [ ] 每份备份有 SHA-256 和原权限记录。
- [ ] 脱敏副本完成格式识别和唯一身份匹配。
- [ ] 无歧义记录自动迁移，歧义记录保持 `relink_required`。
- [ ] PAT 使用旧 AAD 解密、新 AAD 加密，原密钥未更换。
- [ ] 偏好、缓存和密钥未进入 Git 或 Release。
- [ ] 首次启动、第二次启动和历史一致性通过。
- [ ] 0.4.1 回滚使用成套旧数据并验证成功。
- [ ] 回滚影响已向维护者说明。
